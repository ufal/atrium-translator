The second is now experimentally expressible from the same input: both shapes are implemented and the shipped sample set contains both. The decision is deliberately still left to the production/consumer feedback.

## 🔬 The central contract

### AMCR metadata

The current append contract is:

```xml
<amcr:nazev xml:lang="cs">Davle - kultovní areál 1 - klášter sv. Jana Křtitele na Ostrově</amcr:nazev>
<amcr:nazev xml:lang="en">Davle - ritual site 1 - monastery St. John the Baptist on the Island</amcr:nazev>
```

This is deliberately the same-tag / `xml:lang` shape already used by AMCR terminology data. The current sample for `C-N1000019` shows the source and English siblings immediately adjacent and correctly labelled; replace mode contains only the English free-text value. The old degenerate repeated-`pravidla` value is gone from the flagship example.

Controlled-vocabulary elements carrying AMCR `id="HES-…"` / `id="ruian-…"` and their existing Czech `xml:lang` are not translated merely because they carry a language label. The current metadata experiment continues to treat these as vocabulary-backed material.

### ALTO

The current append contract is no longer the first prototype that overwrote `CONTENT` and relabelled the block. It is:

```xml
<String CONTENT="české slovo" ...>
  <ALTERNATIVE PURPOSE="translation:en">English word</ALTERNATIVE>
</String>
```

The source `CONTENT`, geometry, block `LANG`, and 1:1 `String` inventory remain intact. Replace mode still writes English into `CONTENT` and relabels an existing source `LANG` to `en`.

The old measurements from the broken 2026-09-26 pre-fix sample (**2489** blank replace strings / **1300** blank append strings) are obsolete and must not be carried forward. They were caused by the degenerate LINDAT replies and the broken alignment path that `v1.2.0-beta` fixes.

## 🩹 What the 2026-09-26 fix actually fixed

Three separate failures were found in the broken sample refresh and are now covered by code/tests:

1. **Degenerate LINDAT HTTP 200 replies.** One backend replica intermittently returned repeated Czech `pravidla` tokens instead of the requested translation. The probe showed the bad/good alternation behind the load balancer.
2. **Unchecked alignment inputs.** Garbage or collapsed line translations could make the similarity-based aligner put large amounts of text onto one line and leave neighbouring lines empty.
3. **Incorrect ALTO append semantics.** The first append implementation overwrote source `CONTENT`; the current implementation preserves source `CONTENT` and stores English in ALTERNATIVE.

The current quality guard evaluates replies against their source, re-requests suspicious replies, flags failed segments/anchors, and performs an end-of-document retry. If a segment still does not recover, source text is retained and the log records `untranslated` rather than silently emitting garbage.

## 🔁 Follow-up observations from the real refresh

### Language identification

The fixed refresh used `--source_lang auto`. Short Czech OCR blocks can make FastText produce implausible language IDs (`krc`, `yue`, `bod`, `epo`, `swh`). The current resolver therefore follows:

**detected → element label → document language → default `cs`**

and accepts only backend-supported source languages. The refresh successfully processed all 15 AMCR records despite those short-text detection hazards.

### LINDAT behaviour

The sequential AMCR runs still show the same operational signature: every run recorded **37 degenerate replies**, but all final outputs completed successfully. This means the guard is active against the public endpoint in the actual sample refresh, not just in tests.

The known operational issue remains worth handing to the LINDAT operators: the broken response appears to come from one replica behind the round-robin balancer, and a re-request succeeds.

### Provenance and licence

The refreshed paradata records:

- `tool_version = v1.2.0-beta`;
- backend `lindat`;
- `source_lang=auto`;
- target `en`;
- output mode per run;
- the FastText + LINDAT + UDPipe components and their effective licence.

The effective output licence recorded by both current AMCR runs is **CC BY-NC-SA 4.0**. Using `source_lang=auto` means FastText participates in the pipeline and its licence is part of the provenance. A production run should therefore keep the licence posture explicit rather than treating it as incidental.

| # | Finding                                                                                                                                                                                                                                            | Evidence                                                                                                                                                                                                                                                                                | Resolution                                                                                                                                                                                                        |
|---|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 1 | **Document records understated their licence.** `process_single_file()` attached the licence block to the record before the backend's components were logged (they were logged only after the first file; the service logged them after the call). | The committed ALTO record and the first AMCR record of each run state **CC BY-NC 4.0** (`fasttext` only); the other 14 say CC BY-NC-SA 4.0. **The `maxOccurs` answer.** With 2 and 3 fixed, the published AMCR 2.2 schema on the committed samples:

| Samples                                    | Valid      | Errors                                                             |
|--------------------------------------------|------------|--------------------------------------------------------------------|
| source (`my_documents/`)                   | 15 / 15    | —                                                                  |
| replace (`in-place_translated_files/xml/`) | 15 / 15    | —                                                                  |
| append (`appended_translated_files/xml/`)  | **0 / 15** | `xml:lang` not allowed (23×); repeated element "not expected" (8×) |

Both halves of the append pair are rejected, so no variant of the same shape can pass: `xml:lang` is not declared on
`nazev` / `popis` / `poznamka` / `lokalizace_okolnosti`, and none of them may repeat. **ALTO append is valid**: source,
replace and append ALTO all validate against ALTO 3.1 (`ALTERNATIVE` with `PURPOSE` is declared). Decision recorded
with the maintainer: keep both modes and `replace` as the default; document the result; append on AMCR records logs
one WARNING per run.
