## 🎯 Goal

Two asks in one issue, with different shapes:

1. **Operational** — run the shipped tool (LINDAT/CUBBITT default backend, wrapped in the XML editing pipeline) against real ARÚP/ARÚB documents or AMCR metadata objects, in a real environment, and collect feedback. Gated on the repo being "ready by Opus opinion" and compliant with [`ufal/atrium-project#53`](https://github.com/ufal/atrium-project/issues/53).
2. **Design** — decide whether the tool should **replace** `SRC`-language fields with `TRG` (English), or **extend** the input by **appending** `TRG` fields alongside the `SRC` ones.

The second is answered in the only way that survives contact with real data: both shapes are now producible from the same input, so reviewers judge output rather than a proposal.

## 🔬 The big question — what the code now offers

Replace is still the default and still the same two lines it always was (`utils.py:347` for metadata, `:787-791` for ALTO). What is new is that append exists beside it:

```xml
<!-- --output-mode append, on data_samples/my_documents/C-N1000019.xml -->
<amcr:nazev xml:lang="cs">Davle - kultovní areál 1 - klášter sv. Jana Křtitele na Ostrově</amcr:nazev>
<amcr:nazev xml:lang="en">Davle - ritual site 1 - monastery St. John the Baptist on the Island</amcr:nazev>
```

Same tag, same attributes, distinguished by `xml:lang` — **AMCR's own convention, not an invented one**. An AMCR thesaurus record stores a concept as `<amcr:heslo xml:lang="cs">` beside `<amcr:heslo_en>` under one `@id`, and `load_vocab.py:124-134` reads exactly that pair on every glossary build. Before this change the repo *consumed* append-shaped AMCR data while only ever *emitting* replace-shaped output.

The framing that made the design tractable is worth keeping on the record: the tool **already appended at the artifact level and replaced at the field level** — a sibling `_en.xml` file is written, the source file is never touched, and `main.py` describes `--document-json` as an *"accretion model"*. The question was never replace-or-append in the abstract; it was **at what granularity the English lives**.

## 🧾 Evidence from the shipped samples

`data_samples/` is untouched since this digest was first written, so every measurement below still holds against the current tree.

### AMCR metadata

| Observation                                           | Count                                                             | Consequence                                                  |
|-------------------------------------------------------|-------------------------------------------------------------------|--------------------------------------------------------------|
| `xml:lang="cs"` attributes across the 15 samples      | **426**                                                           | AMCR marks language routinely…                               |
| `xml:lang` of any other value                         | **0**                                                             | …but only ever Czech in this corpus                          |
| Element types carrying `xml:lang`                     | **23**, all controlled-vocabulary (`id="HES-…"` / `id="ruian-…"`) | Language tags live on thesaurus terms                        |
| The 3 translated free-text fields carrying `xml:lang` | **0**                                                             | In replace mode the output carries no language marker at all |

In a replace-mode output, `<amcr:okres xml:lang="cs">` still correctly declares Czech while `<amcr:nazev>` two elements away holds English and declares nothing — a harvester cannot tell the file from a Czech original except by reading it. **Append mode closes this**, because both halves of the pair are labelled.

### ALTO — why append is *not* per-`String`

|                | Pages | TextBlocks | TextLines | Strings | `CONTENT=""` | multi-word `CONTENT` |
|----------------|-------|------------|-----------|---------|--------------|----------------------|
| input          | 79    | 1193       | 2095      | 7229    | **0**        | **0**                |
| replace output | 79    | 1193       | 2095      | 7229    | **224**      | **304**              |

**528 of 7229 (7.3%)** of the boxes no longer hold one word, and **none of the 7229 was resized**. The cause is structural: `_align_tokens_to_lines` splits one block translation on whitespace and re-buckets it by `difflib` similarity, so the word-to-box correspondence in the output is **manufactured**. A per-`String` English "alternative" would therefore not be an alternative reading of that word — it would be whichever token the bucketing happened to land there.

That is why append mode **labels ALTO rather than duplicating it**. Shipping per-word append would have multiplied a fiction.

## 🩹 2026-09-26 — the ALTO alignment regression (sample refresh `8522167`)

The refreshed samples were broken, and the numbers above no longer describe what the tool shipped:

| `MTX201501307_anon`   | blank `CONTENT` | multi-word | max words / `String` | `"pravidla"` Strings | log rows with empty target |
|-----------------------|-----------------|------------|----------------------|----------------------|----------------------------|
| June v0.5.0 (above)   | 224             | 304        | 13                   | 0                    | 26                         |
| replace, 2026-09-26   | 2489            | 434        | 3455                 | 2580                 | 305                        |
| append, 2026-09-26    | 1300            | 354        | 2248                 | 434                  | 376                        |

**Root causes.** (1) LINDAT answered HTTP 200 with one Czech word repeated up to ~150 times — nondeterministically, on
the metadata path too — and no backend looked at reply content. (2) Page-level batching (v0.8.0, *after* the June
sample) sends a page's line anchors as one request and validated only its line count; degenerate anchors are never
logged, and the anchor-trusting aligner turned them into 71-word lines beside empty ones. (3) ALTO "append" dropped
the source text, and replace left ABBYY's `LANG="cs"` on English.

**Fix.** One detector (`processors/quality.py`) judges every segment against its source; LINDAT re-requests; batches
are accepted only if every item is plausible; anchors must be plausible for their own line or the line is placed by
word count; failed segments are **flagged and re-run at the end of the same document**, and kept as source if they
never recover. The `_log.csv` gained a `status` column. **ALTO append now keeps `CONTENT` and adds
`<ALTERNATIVE PURPOSE="translation:en">`** — which supersedes the "labels, never duplicates" design recorded below;
replace relabels existing `LANG` to the target.

**Still open:** re-run both modes against the live endpoint (one at a time, not concurrently) to refresh
`data_samples/`, and cut a release carrying the fix.

**Follow-up — language identification.** The first real refresh with the fix (`--source_lang auto`) confirmed the
guard (every degenerate reply recovered on the first re-request) and exposed FastText answering `krc`/`yue`/`bod`/`epo`/
`swh` for short Czech OCR blocks — used verbatim as source languages, never thresholded on the ALTO path, and with `en`
(the target) as the answer whenever detection failed. `processors/language.py` now resolves *detected → element label
→ document language → default source language (`cs`)*, accepting only languages the backend can translate; see the
README section "Source-language identification".

**Follow-up — the intermittent LINDAT failures, diagnosed.** With the guard in place, sequential runs showed the first
request of every batch come back degenerate and its identical re-request succeed, reproducibly to the token across
runs: one broken replica behind a round-robin balancer. Output is correct (every reply recovered), each batch costs
two requests; the first re-request is now immediate and the count is reported per document. **Confirmed** by
`python -m eval.lindat_probe`: `✗✓✗✓…` with fresh connections *and* within one keep-alive session (per-request
round-robin behind `nginx/1.30.1`; bad replies 109 tokens of `pravidla` in ~1.6 s, good ~0.3 s).
**Open:** hand the probe's summary block to the LINDAT operators.

**Follow-up — the logs.** The `_log.csv` is now written beside the output as `.partial` and swapped in when the
document is done (`4a44fb6` had committed both ALTO logs empty, mid-run). The first complete log then showed one more
alignment case: a table column whose block translation merged repeated cells (page 76: 42 numbers → 39) shifted every
later cell by one row and left the last rows blank, all logged `ok`. Such a block — fewer words than lines of text —
is now placed line by line from each cell's own translation.

## 🚧 The former blocking unknown — now a one-command experiment

Whether the AMCR XSD permits a repeated `nazev` / `popis` / `poznamka` (their `maxOccurs`) is still unanswered, and `https://api.aiscr.cz/schema/amcr/2.2/amcr.xsd` remains unreachable from the development environment. **But it is no longer a prerequisite.** It is now a command:

```bash
python main.py ./data_samples/my_documents --xpaths amcr-fields.txt \
    --source_lang cs --output-mode append \
    --xsd https://api.aiscr.cz/schema/amcr/2.2/amcr.xsd
```

A validation failure there **is the answer**, not a defect. This is the most useful thing the implementation round bought: a question that blocked the design now resolves itself on first contact with real data.

Note `--xsd` remains opt-in, warn-only, and is **never applied to ALTO** — `process_alto_xml` takes no schema parameter, so only the metadata path is ever validated.

## ⚠️ What a real production run will expose

- **Throughput is bimodal — and now measured.** `_translate_batch` joins a page's blocks and lines into one call each and falls back to one call per item when the line count does not survive. For the 79-page sample that is roughly **158 calls** against up to **~3288**. The counter now separates the two and logs a per-document summary at WARNING when any fallback fired, so "it was slow" becomes "it fell back on N pages, because the model collapsed the newlines".
- **Re-running is safe in append mode, still not in replace.** Replace re-translates English into English with nothing to notice; append skips.
- **Licence inheritance is unchanged.** `config.txt` defaults to `source_lang = auto`, which loads FastText and pulls **CC BY-NC 4.0** into the licence set; the LINDAT backend contributes **CC BY-NC-SA 4.0**. Passing `--source_lang cs` explicitly avoids the FastText component and is right on a Czech-only corpus anyway. The institutes should be told what licence their output carries *before* the run.
- **The integration lane is still a stub.** `tests/integration/` drives the real handler, pipeline and ALTO reconstruction against `stub_lindat.py`. A `live-backend` job against the real LINDAT hosts exists in `.github/workflows/integration.yml`, is `workflow_dispatch`-only, and **has still never been run** — 0 dispatches. Its own header says to run it *"before a release"*; the beta was cut without it.
