# Strategy — Issue #46: Run the Translator In Production and Settle Replace-vs-Append

## Context

The runtime implementation is now **released and verified against the current sample set**. `v1.2.0-beta`
ships the `replace|append` switch, the degenerate-output guard, the corrected ALTO alignment/append
semantics, safer source-language handling, reliable QA logs, and the API refinements.

The current branch is one documentation/sample-refresh commit beyond the release commit. That extra commit
does not change the runtime contract: it refreshes the evidence used by this issue so that both output modes
are represented by current live-backend samples.

The issue has therefore moved from "make the switch work" to **"prove the release in the intended environment
and record the consumer decision."**

Two things that were still open in the previous plan are now complete:

- `tests/test_output_mode.py` has landed and the switch is no longer relying only on API-level coverage.
- The AMCR metadata samples have been regenerated after the degenerate-output fix, in **both** replace and append modes.

The current independent verification is:

- release CI green, including Docker build/push for both targets and Trivy;
- **812 passed / 3 skipped**, **88.4% coverage**;
- refreshed ALTO samples with current alignment/append semantics;
- refreshed AMCR XML, CSV, Document JSON, and paradata samples;
- 15/15 AMCR documents completed in each mode;
- 37 degenerate LINDAT replies detected and successfully handled in each AMCR run;
- the old repeated-`pravidla` failure is absent from the flagship `C-N1000019` sample.

What remains is not another speculative code patch:

- the **real production-site experiment** has not yet been recorded;
- the **external review report** for #46 has not yet been recorded;
- the AMCR `maxOccurs` question has not yet been exercised with `--xsd`;
- no decision has yet been made about changing the `replace` default.

## Execution Plan

### Phase A — Final release/readiness checks

**A1. Treat `v1.2.0-beta` as the runtime baseline.**

The release commit is `3f2f1b6`. Current `test`/`master` is one docs/sample-refresh commit beyond it.
The current sample paradata still records `tool_version = v1.2.0-beta`, so the refresh is exercising the
same released runtime contract rather than a new untagged algorithm.

Do not reopen the old "missing output-mode tests" item: `tests/test_output_mode.py` is now present and
covers AMCR append, ALTO append/replace, idempotency, and fallback reporting.

**A2. Preserve the current sample-generation discipline.**

The sample README's rule is now part of the operational procedure:

```bash
rm -f data_samples/*/*/paradata/*.json

# one command at a time, waiting for PROCESSING COMPLETE between runs
```

The public LINDAT endpoint must not be hit concurrently from the two sample-mode jobs. The refreshed
AMCR paradata demonstrates why: both sequential runs saw **37** degenerate replies and still finished
15/15 successfully.

**A3. Verify the refreshed samples before tagging an issue-level "ready".**

For AMCR, check:

- 15 XML outputs per mode;
- 15 CSV logs per mode;
- six-column CSV header including `status`;
- 0 skipped files;
- fresh paradata;
- `C-N1000019` has proper English in replace mode;
- `C-N1000019` has adjacent `xml:lang="cs"` / `xml:lang="en"` siblings in append mode;
- no repeated `pravidla` garbage in the flagship output.

For ALTO, check:

- append preserves source `CONTENT`;
- append stores English in `ALTERNATIVE PURPOSE="translation:en"`;
- replace relabels existing source `LANG` to `en`;
- the current replace sample's blank `CONTENT` count is **206/7229**, not the old broken-refresh count;
- append has no blank `CONTENT`;
- the current log uses `status`.

### Phase B — Settle the remaining schema and deployment questions

**B1. Run the AMCR append shape through the schema.**

```bash
python main.py ./data_samples/my_documents --xpaths amcr-fields.txt \
    --source_lang cs --output-mode append \
    --xsd https://api.aiscr.cz/schema/amcr/2.2/amcr.xsd
```

This run is not a new product feature. It answers one concrete question:

> Does AMCR 2.2 accept the repeated same-tag sibling representation used by append mode at the targeted fields?

If validation fails, record the failing paths and move the English representation into a follow-up design issue
(attribute/wrapper/Document JSON/etc.). The output-mode switch itself remains valid.

**B2. Keep the licence posture explicit.**

The current sample run used `source_lang=auto`, and its paradata records an effective output licence of
**CC BY-NC-SA 4.0**. For a real institute run over known-Czech material, decide whether the deployment
should pass `--source_lang cs` explicitly so that FastText is not part of the production dependency chain.

Do not treat the licence as a post-hoc note: it belongs in the handover before the first real run.

**B3. Separate release CI from production acceptance.**

A green release workflow, Docker push, and Trivy result establish that the release artifact built and
passed automated checks. They do **not** substitute for a real ARÚP/ARÚB deployment and review.

The production run must therefore be recorded separately.

### Phase C — Hand over and run the real experiment

**C1. Confirm which corpus is actually being used.**

The issue permits "real documents or metadata objects", but the two choices answer different questions:

- **AMCR metadata** → cleanest test of append vs replace at element level;
- **ALTO/scanned documents** → exercises the translation/alignment/geometry behaviour.

The most useful experiment is the **same corpus in both modes**, so reviewers compare contracts rather
than comparing two different inputs.

**C2. Respect the deployment boundary.**

The receiving institute/environment should run the Docker image inside its own infrastructure. Do not wire
GitHub Actions directly to an ARÚP/ARÚB production environment.

Use the existing ATRIUM deployment material:

- `docs/k8s_deployment.md`;
- `docs/templates/k8s/atrium-service.deployment.yaml`;
- `docs/k8s_acceptance_runbook.md`.

**C3. Record the real acceptance run.**

The production run should capture at least:

- image/tag/commit actually deployed;
- input corpus and number of documents/pages;
- mode (`replace` and/or `append`);
- wall-clock time per document;
- failures/timeouts;
- blank or untranslated outputs;
- observed backend retries;
- whether restart/drain behaviour is acceptable;
- whether downstream AMCR/ALTO consumers accept the resulting shape.

The shared runbook's translator row should become the canonical record.

### Phase D — Collect feedback that directly answers the issue

Show reviewers the **same record twice**.

1. **Artifact contract** — which output shape integrates more naturally with their tooling?
2. **AMCR language semantics** — is the append sibling shape valid and useful to their consumers?
3. **Replace-mode ambiguity** — is an English value without a language attribute acceptable when surrounding
   AMCR controlled fields remain explicitly Czech?
4. **ALTO geometry** — do their consumers need source `CONTENT` preserved, or is English replacement sufficient?
5. **Controlled vocabulary** — should `HES-*` / `ruian-*` fields be looked up from the thesaurus rather than
   translated?
6. **Operational behaviour** — how often did they observe retries, timeouts, or alignment approximations?
7. **Licence** — is the recorded `CC BY-NC-SA 4.0` output licence acceptable for the intended use?

Record answers under `agent_dev_logs/` and in the issue review note.

### Phase E — Decide the default and close the issue

Do **not** decide the default in this plan.

Current runtime default remains:

```text
replace
```

The switch makes either outcome cheap to adopt after feedback.

Once the production run and review are recorded:

- keep `replace` as default, or change the default to `append`;
- record the reason as a consumer/production finding;
- move controlled-vocabulary lookup or schema-driven redesign into a follow-up issue;
- update the changelog/release notes if the default changes;
- close #46 only after the production evidence and the reviewer decision are written down.

## Open questions

1. **Which corpus/recipient is the actual production experiment?** AMCR and ALTO exercise different halves
   of the replace-vs-append question. The issue allows either, but a same-input two-mode comparison is
   the cleanest experiment.
2. **Does the AMCR 2.2 XSD accept repeated same-tag siblings at the targeted paths?** The code can produce
   the shape; the remaining question is schema acceptance in the real consumer contract.
3. **Does the production consumer want English replacement or source+English coexistence?** This is the core
   decision and should come from the experiment, not from the implementation team's preference.
4. **Should controlled-vocabulary fields be looked up rather than translated?** Current vocabulary harvesting
   already knows source/English pairs, but the translator still leaves those fields under the existing
   protected/vocabulary contract.
5. **Should production use `source_lang=cs` rather than `auto`?** The current samples prove the auto detector
   can be made safe, but a Czech-only institute corpus has little reason to pay the FastText dependency cost.
6. **What is the accepted output licence for the real deployment?** Current live sample paradata records
   **CC BY-NC-SA 4.0** as the effective output licence.
7. **What is the exact release artifact used in production?** Runtime code is in `v1.2.0-beta`; the current
   `test` tip adds documentation/sample evidence. The deployment record should therefore name the image/tag,
   not just the branch.
