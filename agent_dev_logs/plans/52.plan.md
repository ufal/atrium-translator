## Context

`resolve_source_language()` treats two different cases the same way:
- a guess it should distrust (low score, short OCR text, an exotic code);
- a confident detection of a real language the backend cannot translate.

Both fall back to the element's label, the document's language, then `cs`. The first fallback is #46's deliberate fix. The second translates Latin or Hungarian with the Czech model and logs the result `ok`; the only trace is a WARNING line the service's caller never sees.

The fix splits the two cases. The first case is unchanged. The second keeps the source text and says so in the CSV and in `limits_applied`, through the path a degenerate reply already takes.

## Execution plan

_⏭ Superseded 2026-10-09 — this is option (b); (a) was chosen. What was built is in the section at the top._

### Phase A — tell the two cases apart (`processors/language.py`)
1. `Resolution.basis` gains the value `unsupported`. In `resolve_source_language()`:
   - when the text passed the letter threshold and the top candidate scores at least `min_confidence` but is not accepted, return `Resolution(<that language>, "unsupported", raw)`;
   - do this before hint and context, but only if no accepted candidate scored above it. A real `de` behind a 0.97 `la` still wins.
   - Everything below the threshold keeps today's order.
2. `LanguageTally` counts `unsupported` resolutions per language, and `summary()` lists them (`unsupported: la×1, hu×1`) next to "FastText guesses not used".
3. A policy setting decides what happens:
   - `UNSUPPORTED_SOURCE_LANG=keep` (proposed default: keep the source text) or `default` (today's behaviour, for a run that wants it);
   - read in `SourceLanguagePolicy.from_env()`; `describe()` reports it in the paradata.

### Phase B — keep the source text (`utils.py`)
4. `_SourceLanguages.resolve()` returns the resolution, not only the code. Its three callers then decide per segment: the metadata loop (`utils.py:~840-866`), the ALTO block path and the TEI/plain path.
   - An `unsupported` segment is not sent to the backend; its source text stays.
   - Its CSV row gets `STATUS_UNTRANSLATED`. The guessed language goes into the empty second column, which today is always `""` in metadata rows (`utils.py:852`). If not there, a new column at the end, with the header updated.
5. One `limits_applied` note per document, through `processors/limit_notes.note()`:
   - limit `lang_id_min_confidence`, effect `skipped`, the count, and a detail naming the languages (`2 segment(s) identified as la, hu, which the backend cannot translate, kept their source text`);
   - this needs `LANG_ID_MIN_CONFIDENCE` declared as an `/info` limit in `tool_limits.py` (local; `atrium_limits.limit(…, 0.5, unit="score")`), read from there by the policy instead of `_env_float`.
6. The record: `translations` gets `untranslated_source_langs: {"la": 1, "hu": 1}` next to `detected_source_lang` (`utils.py:412-414`), only on `auto` runs.

### Phase C — tests and docs
7. `tests/test_language.py`, with the existing `_Candidates` double:
   - `la` 0.97 → basis `unsupported`;
   - `la` 0.97 with `de` 0.6 → `de` detected;
   - `la` 0.3 → today's fallback;
   - under 20 letters → today's fallback;
   - `UNSUPPORTED_SOURCE_LANG=default` → `cs` / `default`.
8. `tests/test_unsupported_language.py`, with a stub identifier and a stub LINDAT (the engines the re-run tests use):
   - a metadata document with a Latin, a Hungarian and a German field → two `untranslated` rows, one translated row, one `limits_applied` note (count 2, both languages);
   - the same through `POST /translate`, so the note reaches the response.
9. Docs:
   - README "Source-language identification" (`README.md:838`): the two cases and the setting;
   - `docs/translation-backends.md` (LINDAT's language set decides how often this happens; `ct2` covers `la`/`hu`);
   - `service/README.md` limits table (the new `lang_id_min_confidence` row);
   - the CONTRIBUTING release row; DEVLOG.
