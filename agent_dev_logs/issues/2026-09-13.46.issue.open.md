### Status update — code side done (By Opus)

`c24f5bc` answers the big question as a **switch**, not a verdict: `--output-mode replace|append`
(also `config.txt`, `OUTPUT_MODE`, and a field on `/translate`). `replace` stays the default, with
output byte-identical to before across all 16 shipped samples.

Append uses AMCR's own convention — same tag, distinguished by `xml:lang`, as the thesaurus already
does for `heslo` / `heslo_en`:

```xml
<amcr:nazev xml:lang="cs">Davle - kultovní areál 1 - klášter sv. Jana Křtitele na Ostrově</amcr:nazev>
<amcr:nazev xml:lang="en">Davle - ritual site 1 - monastery St. John the Baptist on the Island</amcr:nazev>
```

ALTO **labels rather than duplicates** — per-`String` append would multiply a fabricated word-to-box
alignment. Also fixed: `/translate` returned HTTP 200 with metadata untranslated, and the batch
fallback degraded ~20× in call count behind a silent `except: pass`. CI green, 592 tests.

**The AMCR `maxOccurs` question is no longer a blocker** — it is one command:
`--output-mode append --xsd https://api.aiscr.cz/schema/amcr/2.2/amcr.xsd`. A validation failure
there is the answer.

### Status update — ALTO alignment & language identification fixed (By Opus 5.5)

The 8522167 sample refresh ("TODO: fix alto alignment") exposed defects unrelated to the replace/append switch itself. Fixed on `test` in dd8e44b (alignment) and 23c1a8d (language identification).

#### What was wrong
- **LINDAT answered HTTP 200 with garbage.** ~30 % of replies were one Czech word repeated up to ~150× (`pravidla pravidla …`) — for headings and full sentences, in ALTO and AMCR metadata alike, and nondeterministically. Nothing checked reply content.
- **The aligner trusted unvalidated line anchors.** Page-batched anchors were checked only for their line count, and bad anchors are never logged, so replace output ended with **2489** blanked `String`s (June baseline: 224) and 70-word lines next to empty ones.
- **ALTO append dropped the Czech**, and replace left ABBYY's `LANG="cs"` on English text.
- **`--source_lang auto`** used FastText's `krc` / `yue` / `bod` / `epo` / `swh` guesses for short OCR blocks verbatim, ignored confidence on the ALTO path, and fell back to `en` (= the target) whenever detection failed, leaving blocks silently untranslated.

#### What changed
- One content check for every segment (`processors/quality.py`): empty, runaway, truncated or looping output. 0 false flags on June's 1193 blocks and 37 fields; every looping reply of the September runs caught.
- LINDAT re-requests degenerate replies (`LINDAT_GUARD_RETRIES`). A batch is accepted only if every item is plausible. A line whose anchor is unusable is placed by source word count.
- Failed segments are **flagged and re-run at the end of the same document** (`TRANSLATION_RERUN_ROUNDS`, `TRANSLATION_RERUN_DELAY_S`). A segment that never recovers keeps its source text: never blanked, never garbage.
- `_log.csv` gains a `status` column (`ok` / `rerun` / `approx_alignment` / `untranslated`) and is written in document order.
- ALTO **append** keeps every `CONTENT` and adds `<ALTERNATIVE PURPOSE="translation:en">`; **replace** relabels existing `LANG` to `en`.
- Language: a FastText guess is used only if the text is long enough, the guess confident enough, and the language one the backend can translate. Otherwise: the block's `LANG` / `xml:lang` → the document's language → the default source language (`--default-source-lang` / `DEFAULT_SOURCE_LANG`, `cs`). The result is recorded as `translations.detected_source_lang`.

#### Evidence
Offline, 79-page ALTO sample, same injected faults (~30 % looping replies) for both code versions:

| | before | after |
|---|---|---|
| blank `String`s (replace) | 1752 | 3 |
| garbage `String`s | 294 | 0 |
| `_log.csv` rows with empty target | 498 | 0 |
| append: `CONTENT` unchanged | 0 / 7229 | 7229 / 7229 |
| metadata fields with garbage | 8 / 37 | 0 |
| UDPipe "no model" languages (`auto`) | 5 | 0 |

783 unit + 7 integration tests pass, coverage 88 %. In the first live run, every degenerate LINDAT reply in pages 1–12 was recovered by the first re-request.
