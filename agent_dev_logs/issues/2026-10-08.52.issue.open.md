# [\#52 Issue](https://github.com/ufal/atrium-translator/issues/52) `open`: An unsupported source language is translated as Czech without telling the caller
**Labels**: `bug`, `question`


#### <img src="https://avatars.githubusercontent.com/u/65828620?u=80b39d3cb2967c52e1d4af28dcefc7a1efdfdc79&v=4" width="50">[K4TEL](https://github.com/K4TEL) opened issue at [2026-10-08 12:17](https://github.com/ufal/atrium-translator/issues/52):

With `source_lang=auto`, the identifier's answer is used only if the backend can translate that language. Otherwise the segment falls back to the element's label, the document's language, then the default `cs`, and goes to the Czech model. With a stub identifier, a Latin line (`la`, 0.97) and a Hungarian one (`hu`, 0.99) are both translated as `cs` (basis `default`); a German one stays `de`.

The only trace is one log line per document (`FastText guesses not used: la×1, hu×1`). The response, `limits_applied`, the `_log.csv` status and the paradata say nothing, so the result (plausible nonsense or an untranslated copy) is logged `ok`. The pilot (`--source_lang cs`) is not affected; an `auto` run over mixed archive material (Latin taxa, German and Hungarian passages) is.

**To decide:** (a) report it: a `limits_applied` note with the count and the guessed languages, and a distinct CSV `status`; or (b) refuse it per segment: keep the source text and log `untranslated`, as for a degenerate reply. Either way, a test with a stub identifier (`la`, `hu`) shows the signal in the response and the CSV.
